# 注释检查

对项目代码进行三个维度的注释质量审查：**完整性**、**准确性**、**可读性**。

---

## 审查流程

### 第一步：确定审查范围

- 用户指定了文件/目录（`$ARGUMENTS`）→ 审查该范围
- 用户没指定 → 询问要审查哪个文件，或建议审查最近修改的代码

### 第二步：逐维度检查

#### 维度一：注释完整性（有没有写注释）

**标准**：每 10 行代码中，至少应包含 3 行注释（约 30% 的注释密度）。

**检查方法**：
1. 统计目标文件总行数（排除空行和纯 import/export 行）
2. 统计注释行数（`//` 和 `/* */`）
3. 计算注释密度 = 注释行数 / 有效代码行数
4. 逐函数检查：每个函数是否有关键注释（函数用途、参数说明、返回值）

**判定标准**：
| 注释密度 | 评价 |
|----------|------|
| ≥ 30% | 🟢 良好 |
| 15% ~ 30% | 🟡 偏少，需补充 |
| < 15% | 🔴 严重不足 |

**重点检查**：
- 每个函数/方法前是否有注释说明"做什么"
- 复杂逻辑（嵌套循环、正则、算法）是否有解释
- 特殊处理（hack、workaround、边界情况）是否有标注
- 类型定义、接口、枚举是否有字段说明

#### 维度二：注释准确性（写对了没有）

**检查方法**：
1. 逐一比对注释描述与代码实际行为
2. 检查是否存在"注释说A，代码做B"的情况
3. 检查注释中的参数名、返回值、异常说明是否与代码一致
4. 检查注释是否过期——代码已改但注释未更新

**常见问题**：
- 复制粘贴的注释，内容与当前函数不符
- 参数名在重构后未同步更新
- 注释描述的功能已被删除或重写
- 注释中的数字、阈值、URL 是否仍然有效

#### 维度三：注释可读性（小白看得懂吗）

**标准**：注释应以"不懂编程的人也能大致理解"为目标。

**检查方法**：
1. 注释是否使用了专业术语但未解释（如"memoization"、"debounce"、"serialize"）
2. 注释是否为英文混写中文的"散装英语"（如"// 调用 fetch API 获取 user 列表，用 async/await 处理 response"）
3. 注释是否解释了"为什么这样做"而不仅仅是"做了什么"

**好的注释示例**：
```typescript
// ✅ 小白看得懂
// 把用户输入的数字转成带两位小数的金额格式
// 比如：用户输入 25 → 显示 "¥25.00"

// ❌ 只有懂编程的人看得懂
// format currency with toFixed(2)
```

**判定原则**：
- 注释应优先使用中文
- 技术术语需要时保留，但加上简短解释
- 优先解释"为什么"（业务意图），而不是"是什么"（代码行为）

## 输出格式

审查完成后，按以下结构输出报告：

```
## 注释审查报告：<文件名>

### 📊 总览
| 文件 | 有效行 | 注释行 | 密度 | 评级 |
|------|--------|--------|------|------|

### 🔴 注释缺失（完整性）
- 第 X 行：`function xxx()` — 缺少函数用途说明
- 第 Y 行：复杂逻辑块 — 需加注释解释

### 🟡 注释不匹配（准确性）
- 第 X 行：注释说"...", 但代码实际是"..."

### 🟠 注释难懂（可读性）
- 第 X 行："fetch data" — 应改为中文说明取什么数据

### ✅ 改进建议（按优先级排）
1. 优先补充缺失的函数注释
2. 修复不匹配的注释
3. 优化难懂的注释表述
```

---

## 审查原则

1. **不是写论文**：注释求清晰不追求长度，一句话说清楚即可
2. **不为注释而注释**：`let x = 1; // 给 x 赋值为 1` 是无价值注释，不鼓励
3. **重点看意图**：解释"为什么这么做"比解释"代码在做什么"更重要
4. **用中文优先**：面向中文用户的项目，注释用中文写
